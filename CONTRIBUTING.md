# Вклад в AgilFrame

**Русский** · [English](CONTRIBUTING.en.md)

Вопросы по установке сверяйте с [документацией](https://github.com/GillHD/agilframe-core/blob/main/docs/README.md). Для ошибки или предложения используйте [форму Issue](https://github.com/GillHD/agilframe-websdk/issues/new/choose). Об уязвимостях сообщайте [приватно](SECURITY.md).

## Issue

- Одна задача на один результат. В заголовке укажите компонент и наблюдаемую проблему или требуемый результат.
- Для ошибки укажите версию или SHA, окружение, роли, шаги через штатный интерфейс, ожидаемое и фактическое поведение. Для UI добавьте тему, ширину окна и обезличенный скриншот. Для мультинодового случая укажите топологию.
- Для предложения опишите пользователя, задачу, предлагаемый результат и критерии приёмки. Для изменений API укажите совместимость и необходимость миграции.
- Удалите из вложений токены, ключи, персональные данные, приватные URL и содержимое корпоративных звонков.

## Код

1. Создайте короткоживущую ветку от актуальной `main`. Один pull request решает одну связанную задачу.
2. Переиспользуйте существующие интерфейсы, проверки прав и компоненты. Изменения REST, WebSocket и конфигурации проверьте на совместимость с текущим SDK и ранее сохранёнными данными.
3. Для исправленного дефекта добавьте регрессионный сценарий, если действующие тесты его пропускают. Изменения сценария использования отражайте в документации. Оставляйте сборки, кэши и личные настройки инструментов в локальном окружении.
4. Делайте коммиты под своей GitHub-учётной записью с собственным подтверждённым или GitHub no-reply адресом. В заголовке пишите, что изменилось. Для технического решения поясните причину в теле коммита или PR.

Команды проверки этого компонента приведены в [README](README.md).

Укажите фактически выполненные проверки. Для браузерных изменений приложите сценарий проверки и подтверждение результата. Опишите причину каждого пропуска, влияющего на приёмку.

## Изменения с использованием ИИ

Если инструмент ИИ написал или переписал существенную часть изменения, укажите в PR затронутый модуль и выполненные проверки. Автор PR лично читает весь предлагаемый diff, включая тесты и конфигурацию. Он проверяет корректность, безопасность, лицензии, обработку ошибок и совместимость. Автор остаётся ответственным за код и должен уметь объяснить решение на ревью. Для изменений с последствиями проводите обычный человеческий review по правилам проекта.

## Pull request и review

- Укажите, зачем нужно изменение, что увидит пользователь и какие проверки проведены. Ссылайтесь на задачу через `Fixes #123`, если PR закрывает её полностью. Черновик помечайте Draft.
- Заранее обсудите с сопровождающим изменения авторизации, схем данных, публичных API и лицензии. Для таких изменений опишите совместимость, обновление, откат и ограничения.
- Ревьюер проверяет заявленное поведение, границы доступа, обратную совместимость и тесты. К слиянию должны быть устранены блокирующие замечания и пройти применимые проверки CI. Автосгенерированный комментарий сам по себе не подтверждает человеческое review.
- Передавайте изменения, на которые у вас есть право. Лицензия проекта и сторонние уведомления описаны в [LICENSE](LICENSE) и [NOTICE](NOTICE). Перед коммерческим перелицензированием внешних вкладов сопровождающий отдельно проверяет необходимые права.
